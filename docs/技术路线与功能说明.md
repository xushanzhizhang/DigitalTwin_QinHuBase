# 琴湖基地智慧农业数字孪生 · 技术路线与功能说明

> 徐州生物工程职业技术学院 · 农林实训基地（琴湖基地）
> 面向：项目验收汇报、后续开发交接、对外演示讲解

---

## 一、项目定位

琴湖基地是学校农林类专业的实训场地。本项目不是做一个"好看的三维大屏"，而是给这块
真实的基地建一套**可运营的数字孪生**：

> 现场有什么（模型）→ 现在什么状态（传感器）→ 为什么是这个状态（物理模型）
> → 该怎么做（决策 Agent）→ 做完什么效果（回写模型并留痕）

普通三维可视化止步于第二步，本项目的差别在后三步。这也决定了技术选型：
**模型是载体，数据是主线，决策是价值点**。

## 二、总体架构

```
┌──────────────────────────────────────────────────────────────┐
│  展示层   Web 大屏（Three.js + ECharts）                       │
│          三维孪生场景、KPI、趋势曲线、决策流、控制台            │
└───────────────▲──────────────────────────┬───────────────────┘
                │ WebSocket 帧（8 Hz）      │ 控制指令
┌───────────────┴──────────────────────────▼───────────────────┐
│  服务层   FastAPI + Uvicorn                                    │
│          REST：站点配置、历史曲线、决策检索、传感器注册          │
│          WS  ：实时帧推送、决策事件                             │
│          存储：SQLite 时序表（采样 60 s 落盘）                  │
└───────────────▲──────────────────────────┬───────────────────┘
                │ 状态快照                  │ 指令
┌───────────────┴──────────────────────────▼───────────────────┐
│  孪生内核                                                      │
│  ├ 传感器接口层  SensorSource 抽象（模拟 / Modbus / MQTT / HTTP）│
│  ├ 物理模型层    太阳辐射、蒸散、湿度换算、温室能量与水量平衡     │
│  ├ 模拟器        5 个分区状态推进（昼夜节律 + 天气过程）         │
│  └ 决策 Agent    规则库 + 冲突消解 + 死区/保持时间 + 留痕        │
└───────────────▲──────────────────────────────────────────────┘
                │ glb 资产
┌───────────────┴──────────────────────────────────────────────┐
│  模型层   qinhu_base_digital_twin.glb + scene_manifest.json    │
│          5 个区域组、945 网格、83 万面、43 材质                 │
└──────────────────────────────────────────────────────────────┘
```

**数据流（一个控制周期的完整闭环）**

```
模拟器/真实传感器 → 状态快照 → 决策 Agent 评估
        → 生成指令（含依据与预期）→ 写回执行器状态
        → 下一周期状态变化 → 通过 WS 推到大屏 → 驱动模型构件
```

这条链路是闭环的：Agent 开了风机，下一周期的棚温就会降，大屏上的风机在转、温度在掉、
决策流里有这条记录 —— 三者是同一条因果链，而不是三份互不相干的数据。

## 三、模型层

### 3.1 资产

主模型由建模流程产出（Blender 系），运行时只加载一份 `qinhu_base_digital_twin.glb`
与 `scene_manifest.json`。详细结构与优化见《模型资产说明.md》。

### 3.2 运行时工程化

`frontend/js/scene/site.js` 负责把"美术模型"变成"可运营场景"：

1. 材质工程化（薄膜半透、钢件金属度、水面替换）；
2. 阴影策略（只给承重构件投影，作物行不投影）；
3. 静态合并（按区域 × 材质，945 → 约 380 网格）；
4. **构件索引**（靠模型命名识别风机叶片、状态灯、作物行、棚膜）；
5. 暴露孪生 API（`setRegion` / `applyState` / `update`）。

### 3.3 命名即接口

模型里的节点命名就是数据绑定的接口，例如 `0786_园艺中心_连栋1_排风机叶片`。
好处是：模型微调不影响代码，只要命名不变；坏处是改名会静默失效，所以
《模型资产说明.md》里把命名契约单独列了一节。

## 四、传感器接入层

### 4.1 抽象

`backend/sensors/base.py` 定义统一接口：

```python
class SensorSource:
    def read(self) -> dict[str, float]: ...   # 返回 {metric: value}
    def meta(self) -> dict: ...               # 设备信息、单位、量程
```

实现类：
- `SimulatedSource` —— 当前使用，接模拟器；
- `ModbusSource` / `MqttSource` / `HttpSource` —— 预留骨架，实现 `read()` 即可接入。

**接入真实传感器的改动面**：只改 `backend/config.py` 里 `SENSOR_NODES[].protocol`，
以及对应适配器的连接参数。前端与决策层零改动。

### 4.2 模拟器不是随机数

`backend/sensors/physics.py` + `simulator.py` 实现了一套简化但自洽的物理：

- 太阳位置（赤纬 + 时角）→ 太阳高度角 → 法向直射/散射 → 温室内的 PAR；
- 温室能量平衡：太阳得热、围护结构传热、通风换气、湿帘降温、蒸腾潜热；
- 水量平衡：根区含水率按蒸散消耗、灌溉补给、深层渗漏推进；
- 湿度用绝对湿度演算，再由温度反算相对湿度（避免 RH 与 T 脱耦）；
- 天气过程用 OU 过程（均值回复），云量、气温异常不会随机游走。

验证过的指标：连续 7 天数值稳定、昼夜曲线符合节律、灌溉阈值按水分亏缺（MAD=45%）标定。

### 4.3 五个分区

| 分区 | 名称 | 作物 | 类型 |
|---|---|---|---|
| Z1 | 琴湖景观区 | — | 水体 + 气象 |
| Z2 | 园艺植物生产实训中心 | 番茄 | 三连栋薄膜温室 |
| Z3 | 芍药种质资源创新基地 | 芍药 | 三栋低拱棚 |
| Z4 | 数智农业实践研学中心 | 叶菜（水培） | 砖墙+膜温室 |
| Z5 | 露地栽培与苗床区 | 草莓 | 露地 |

## 五、决策 Agent

### 5.1 设计原则

1. **可解释**：每条决策都带触发依据（当前值 vs 阈值）、农艺依据、预期效果；
2. **不抖**：死区 + 最短保持时间 + 指令量化，避免执行器反复动作；
3. **有优先级**：紧急（防冻、防热害）> 重要（通风、遮阳）> 优化（补光、CO₂）> 节能；
4. **留痕节流**：同一分区同一执行器 30 min 内不重复记录，信息流不被淹没。

### 5.2 规则库

| 规则 | 触发 | 动作 | 依据 |
|---|---|---|---|
| R1 通风 | 棚温超适温上限 / RH>88% | 卷膜开度 | 温度优先、湿度其次，夜间以保温为先 |
| R2 湿帘风机 | 棚温超上限且外温低于棚温 | 湿帘开度 | 蒸发降温，效率随外湿下降 |
| R3 外遮阳 | 冠层辐射超阈值 | 遮阳网开度 | 夏季正午强光抑制光合 |
| R4 加温 | 低于绝对下限 / 适温下限 | 加温档位 | 防冻优先于节能 |
| R5 补光 | 光积累不足（DLI 缺口） | 补光强度 | 连阴天补光 |
| R6 灌溉 | 根区含水率低于 MAD 下限 | 滴灌量 mm | 按水分亏缺灌溉，不按固定周期 |
| R7 休眠期管理 | 芍药休眠期 | 控水、排湿、不加温 | 越冬控水可显著降低腐烂率 |

### 5.3 参数标定（实测记录）

- 通风增益从 15 %/℃ 降到 9 %/℃：执行机构 15 min 滞后与比例带同量级，增益过高会等幅振荡；
- 决策周期 60 s → 120 s，通风死区 10%，最短保持 10 min：通风指令从每天 77 条降到约 10 条；
- 灌溉阈值按 `lower = FC − 0.45 × (FC − WP)` 重标定。

## 六、服务层

### 6.1 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/site` | 站点配置：分区、传感器节点、执行器、机位 |
| GET | `/api/state` | 当前快照：环境、分区状态、KPI、存储统计 |
| GET | `/api/history?minutes=&zone=` | 历史曲线（等间隔抽样，默认 240 点） |
| GET | `/api/decisions?limit=` | 决策留痕（含依据与预期） |
| GET | `/api/health` | 健康检查 |
| POST | `/api/command` | 手动下发执行器指令 |
| POST | `/api/sensor` | **真实传感器写入入口**（带 token） |
| WS | `/ws` | 实时帧（8 Hz）+ Agent 快照（2 s） |

### 6.2 时间处理

演示场景下仿真时钟可能领先真实时间数小时，因此：

- 历史查询用**仿真时刻**过滤（`now_ts`），否则曲线会全空；
- 启动时若真实时间在 07:00–17:00 之外，自动把仿真起点挪到当天 09:30，保证打开就是白天；
- 环境变量 `TWIN_START_HOUR` / `TWIN_SPEED` 可锁定起始时刻与倍速，方便演示与截图。

## 十三、渲染稳定性与初始视角

大屏是要长时间挂着的，所以"画面稳"和"数据准"同等重要。这一节记录两条必须守住的约束。

### 13.1 任何"每帧变化"的对象都要能被单独关掉

画面上一旦出现闪烁，最快的定位办法是**二分关闭**：关水面、关阴影、关动画对象，
每关一项就连拍若干帧做逐像素差分（找"上一帧<200、本帧>248"的新增纯白像素）。

本轮就是靠这个办法定位到风机叶片的：单帧看不出异常，连续帧一比就发现有一片
0.3×0.8 m 的白片在绕场地中心扫圆（详见《模型资产说明》第 8 节）。

**约定**：

- 风机、水面、状态灯各自有独立开关（`site.fans[].speed`、`water.mesh.visible`、
  `lamp.mat.emissiveIntensity`），排查时可以直接在控制台置零；
- 模型页提供 `__freezeWater` / `__waterT` 冻结水面相位，便于逐帧比对；
- 加载静态合并开关 `?merge=0`，可按原始节点名排查结构。

### 13.2 细构件的高光必须"钝"一点

温室骨架是成百上千根 50 mm 的细杆。roughness 给到 0.45 时，每根杆上的太阳高光
只有一两像素宽，视角一动就成片地闪。现在的口径：

| 材质 | roughness | metalness | envMapIntensity |
|---|---|---|---|
| 镀锌钢/钢构 | ≥ 0.58 | ≤ 0.55 | 0.7 |
| 农膜 | 0.62 | 0 | 0.55 |
| 透光板 | 0.34 | 0.1 | 0.7 |

### 13.3 初始视角

模型入口在东侧，所以"进门第一眼"是**自东向西**。

`buildViews()` 里的 `entry` 视角不写死坐标：它遍历模型找 `入口门柱/门头`，
取门中心，再往门内退 6 m、眼高 1.75 m、看向正西。换模型、改门位都能自动跟上。

主界面与模型页共用这个机位；模型页仍可用 `?cam=&tgt=&fov=` 覆盖，便于定点核对。
